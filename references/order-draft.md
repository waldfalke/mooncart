# `order-draft.json`: правила данных

## Принципы

1. **Свидетельство предшествует утверждению.** Значение попадает в draft только после наблюдения в текущем браузерном состоянии; `evidence.paths` указывает, какие JSON-поля поддержаны этим наблюдением.
2. **Неизвестное остаётся неизвестным.** Отсутствующее значение хранится как `null`, если схема это допускает, а причина — в `issues`. Значение не восстанавливается из «обычной цены», памяти модели или похожего варианта.
3. **Одна строка — один покупаемый вариант.** Разные размеры, цвета или комплектации имеют разные `line_id`, даже если страница объединяет их под одним названием.
4. **Деньги не перераспределяются.** Сохраняются число и исходная валюта страницы. Скидка уровня заказа остаётся в `totals.discount`, если магазин не показал её на строках.
5. **Состояние монотонно.** `captured` означает сохранённые наблюдения; `validated` — прошедшую схему и смысловые проверки полноту; `prepared` — заполненную и прочитанную обратно форму без отправки.
6. **Рабочий draft не содержит личности.** Логины, cookies, email, телефоны, адреса, реквизиты и account IDs не сохраняются даже когда видны на странице.
7. **URL — тоже данные.** Перед записью удалить userinfo, query и fragment. Если сам path персонализирован или подписан, получить публичный URL; до этого хранить безопасный URL и blocker.

## Поля

| Поле | Смысл |
|---|---|
| `session_id` | Стабильное имя одной сессии одного магазина, например дата-время и slug магазина |
| `merchant.name` | Наблюдённое имя магазина; `null` допустим только в неполном `captured` с issue |
| `merchant.page_url` | Страница товара или корзины, служившая входом capture |
| `merchant.currency` | ISO 4217 код; `null` допустим только в неполном `captured` |
| `items` | Только наблюдённые товарные строки; `[]` допустим только в `captured` с blocker на `/items` |
| `items[].product_url` | URL позиции; `null` допустим только в неполном `captured`, если корзина его не раскрыла |
| `items[].title` | Наблюдённое название; `null` допустим только в неполном `captured` с issue |
| `items[].brand` | Бренд из страницы; опциональное непустое поле, не выбранный вариант |
| `items[].item_type` | Вид товара из merchant page; опциональное непустое поле, не готовый ID категории партнёра |
| `items[].variant` | Набор выбранных атрибутов с короткими ключами: `size`, `color`, `style` |
| `items[].unit_price` | Наблюдённая цена одной единицы; не вычислять из общей суммы |
| `items[].line_total` | Наблюдённая сумма строки; `null`, если страница её не показала |
| `evidence[].paths` | JSON Pointer-пути полей, увиденных в одном источнике одним способом |
| `issues[]` | Неоднозначности и препятствия; `blocker` запрещает переход в `validated` |
| `route` | Выбранный пользователем forwarder и конкретная форма |
| `route.merchant_country`, `route.warehouse` | Выбранные значения формы маршрута, без адреса склада или идентификатора аккаунта |
| `handoff` | Результат read-back; `submitted` всегда `false` |

## `capture`

Если выбран партнёр с сохранённым профилем в `references/partners/`, прочитать его перед сбором и сопоставить нужные товарные поля с магазином. Профиль хранит наблюдение, а не гарантирует действующие требования: при handoff сверить его с живой формой. Отсутствующие обязательные данные становятся blockers; бренд и тип не прятать в variant.

Если барьер возник до наблюдения товаров, всё равно сохранить `order-draft.json`: безопасный URL страницы и его evidence, неизвестные name/currency как `null` с отдельными issues, `items: []` с blocker на `/items`. Не создавать фиктивный товар из URL или пользовательского запроса. Если строка товара видна, но название отсутствует, сохранить наблюдённые поля этой строки и `title: null` с issue. Эти послабления относятся только к `captured`; schema_version остаётся 1.0, прежние полные drafts совместимы.

1. Получить свежий Playwright snapshot выбранной страницы.
2. Создать `stand/<session-id>/order-draft.json` со статусом `captured`.
3. Считать selected state контролов, а не соседний текст всех доступных вариантов.
4. Записать timestamps с часовым поясом и evidence для фактически увиденных полей.
5. Любой барьер или неоднозначность записать в `issues`; сохранить частичный draft до остановки.
6. Если сумма видна, а валюта не установлена, оставить числовые денежные поля `null` и описать наблюдавшуюся строку в issue.
7. Запустить `python <skill-root>/scripts/validate_order_draft.py <draft>`.

## `validate`

- `scripts/validate_order_draft.py` завершился с кодом 0; один только разбор JSON или schema check недостаточен.
- Каждый ненулевой коммерческий факт поддержан хотя бы одним evidence path.
- Нет `blocker`, дубликатов `line_id` и смешения магазинов.
- `quantity` и `unit_price` известны для каждой строки, валюта известна.
- Наблюдено имя магазина, есть хотя бы одна товарная строка и известны названия всех строк. Неполный capture сначала дополняется свежими наблюдениями; его нельзя повысить удалением blockers.
- Итоги не объявляются согласованными только потому, что модель смогла их пересчитать: приоритет у наблюдавшихся значений страницы и явно записанных расхождений.

После успешных проверок установить `validated_at` и `status: "validated"`, затем снова запустить validator. Только его код 0 разрешает оставить новый статус.

## Кэш локаторов партнёра

После первого наблюдённого прохода сохранять адреса найденных полей в выбранном профиле `references/partners/`: декларативный `locator` (CSS selector либо role/label/text с точным именем), видимую подпись, тип контрола, безопасный URL формы и время наблюдения. Не сохранять исполняемый код, временные snapshot refs, значения личности или сессионные токены. Для составного виджета отдельно хранить адрес чтения значения и адреса видимых контролов ввода.

При следующем проходе сначала проверить текущие URL/заголовок формы и сохранённые локаторы. Достаточна прицельная проверка нужных полей: единственное совпадение, ожидаемые label/тип и нужная товарная строка; для ввода — доступный видимый контрол. Совпавший ID с изменившейся подписью тоже означает промах. Только после этого обращаться к полю; коммерческие значения, валюта и доступные варианты всё равно устанавливаются по текущему UI/draft, не по кэшу.

При отсутствии кэша, нуле или нескольких совпадениях, изменившейся подписи/типе либо неудаче действия искать поле по живым labels/roles: сначала в его участке формы, затем шире, если участок не найден. После успешного поиска обновить только затронутые адреса и их время/основание наблюдения. Если смысл поля или соответствие строки остались неоднозначными, остановиться с issue. Не повторять слепо неработающий locator и не выбирать `.first()` для устранения неоднозначности.

`{row_index}` в профиле означает наблюдённый индекс DOM, не порядковый номер `items[]`. До заполнения установить соответствие draft lines и живых строк; после добавления/удаления строк проверить его снова. Кэш не заменяет read-back и не расширяет полномочия на оферту, изменение цены или отправку.

## `handoff`

Страна магазина и страна доставки до склада могут различаться. Выбор страны/склада опирается на смысл полей партнёра, условия merchant shipping и маршрут пользователя, а не домен магазина. В totals сохранять только наблюдённую стоимость доставки для выбранного направления; опубликованный тариф до проверки корзины не выдавать за окончательный checkout. Тип товара сопоставить с фактической категорией формы по смыслу, сохранив исходный merchant item_type; при неоднозначности остановиться с blocker. Ненулевые brand/item_type и выбранные country/warehouse требуют evidence и read-back наравне с остальными данными. Эти поля добавлены к schema_version 1.0 опционально; прежние drafts остаются совместимы.

1. Работать с `validated` draft либо с явно возобновляемым `prepared` draft, повторно прошедшим validator, и формой, выбранной пользователем. `prepared` свидетельствует о прошлом read-back, а не о сохранении формы на стороне партнёра: если вкладка закрыта или недоступна, восстановить поля и обновить read-back/`prepared_at` по текущему UI.
2. Снять snapshot формы; использовать проверенный кэш партнёра, а при промахе найти нужные поля по живым labels/roles, как описано выше.
3. Заполнить только draft-backed данные. Поля личности и оплаты оставить нетронутыми.
4. Снять новый snapshot, прочитать значения обратно и сравнить каждое заполненное поле.
5. Записать `route`, `handoff.verified_fields`, незаполненные поля и `submitted: false`.
6. Установить `prepared_at`, `status: "prepared"`, добавить `form_readback` evidence с JSON Pointer-путями, запустить validator и остановиться до Submit/Pay/Place order.

  "session_id": "20261009-190000-example-sports",
  "status": "validated",

  "validated_at": "2026-10-09T19:02:00+03:00",
  "prepared_at": null,
  "merchant": {
    "name": "Example Sports",
    "page_url": "https://merchant.example/cart",
    "currency": "USD"
  },
  "items": [
    {
      "line_id": "line-001",
